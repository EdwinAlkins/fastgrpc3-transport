# Lot 1 results — server streams through variant B, 30/10/2026

Same machine and versions as `2026-10-30.md`. `bench/stream_bench.py`: the server, pinned to
CPU 0, streams 200,000 medium messages (287 B, each encoded by `MessageCodec` as fastgrpc3
does) for one `Small(id=200000)` request; the client, pinned to CPUs 2–3, reads them with
raw `grpc.aio`, without decoding. "Slow": the client sleeps 1 ms every 100 messages, so that
backpressure stays engaged for the whole stream. Server RSS sampled at each tenth.

## Reading

- **Lot 1's exit condition is met**: memory stays flat over 200,000 messages, with a fast
  and with a slow reader; no stall; backpressure demonstrated (below).
- Streams gain less than unary calls (1.8× with a fast reader): the Python client reading
  50,000 messages/s on two CPUs is probably the limit now; the server side does one
  `MessageCodec.encode` and one `try_send` per message, with no wake-up while the channel
  has room.
- **Backpressure** (`tests/python/test_queue.py::test_a_reader_that_stops_stops_the_producer`):
  a stream of 40,000 messages of 1 KB; the client reads one message, then stops for 0.8 s.
  The producer stops after 4,000–7,000 messages (three runs) and stays still, then resumes
  when the client reads again, and the stream completes. What it produced meanwhile is the
  bounded channel (16 messages), tonic's and HTTP/2's buffers, and the receive window the
  grpc C-core client grows on its own (a few MB): bounded, whatever the stream's length.
  With 8-byte messages the whole stream (2.6 MB) fits in that window, which is why the test
  uses 1 KB.
- **Cancellation**: a client that cancels closes the channel; the handler's next `send`
  returns `False` and the handler returns (`test_a_client_that_cancels_stops_the_producer`).
